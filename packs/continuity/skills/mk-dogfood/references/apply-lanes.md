# Apply lanes

Steps for each lane once a proposal is accepted (`--apply`, or the user's yes under `--ask`). Run a lane's checks before reporting it applied. When a command or flag is missing, check its live help (`mk <command> help`) and report the gap instead of guessing.

## Contributor lane (max-kit pack skill, user can push)

The max-kit checkout's own `CLAUDE.md` or `AGENTS.md` owns its delivery gates (commit policy, PR body, landing) and wins over this list. Read it before the first commit; this list only adds what is specific to a dogfood change.

1. **Locate the checkout.** Run `python scripts/find_max_kit_repo.py` from this skill's directory (use `python3` where `python` is Python 2). It checks `$MAX_KIT_REPO`, the parent of `$MAX_KIT_PACKS_DIR`, the working directory, then scans common code folders and, on Windows, each drive. Use `repo.path` when `repo.verified` is true. When nothing verifies, ask the user for the path. When the scan found it, suggest persisting `MAX_KIT_REPO=<path>` in the user's shell profile so later runs skip the scan.
2. **Confirm push access** with `gh api repos/tinhtran24/max-kit --jq .permissions.push`. Anything other than `true` moves the proposal to the proposal lane.
3. **Isolate the change** in a new worktree branched from the canonical remote's `main` (`repo.canonical_remote`), with `mk-worktree` (`create`) when installed, else `git -C <repo> worktree add <dir> -b dogfood/<slug> <remote>/main`. Never edit the checkout's current working tree; another session or the user may own it.
4. **Find the source.** The installed `mk-<slug>` comes from `packs/<pack>/skills/mk-<slug>/`; `mk skills list` and the pack's `pack.json` say which pack.
5. **Edit, bump and validate.** Bump `metadata.version` (patch for a fix, minor for new behaviour), then run the pack-skill checks of `mk-skill-creator` (its pack skill contract lists them: `quick_validate.py`, `lint_cruft.py --routing`, `mk skills lint`, `mk check`) and the skill's own script tests when scripts changed.
6. **Commit, push and open the PR into `main`** following the repository instructions, with `mk-git` (`cm`, `pr`) when installed. Search open and closed issues first and link matches, and summarise the session evidence in one line, described, never quoted. Nothing from the transcript goes into the diff, message or PR. Open it ready for review and stop.
7. **Do not patch installed copies.** `.claude/skills/` and `.agents/skills/` are rendered by `mk sync` and are overwritten on the next sync or `npm install`. The fix reaches the user's knowledgebases when the PR merges and they update max-kit; say so in the report.

## Proposal lane (max-kit pack skill, user cannot push)

Do not edit installed copies (they are regenerated by `mk sync`). Give the hunk in the report and offer an issue or a PR from the user's fork of the max-kit repository.

## In-place lane (user or project authored skill)

Copy the files the change touches to a scratch folder, apply the hunk, bump `metadata.version` when the skill has one, and run `quick_validate.py` and `lint_cruft.py` from `mk-skill-creator` against the skill directory.

## Proposal-only lane (plugin or third-party skill)

Do not edit the installed files. Give the hunk in the report and, when the user wants it, offer an upstream issue or a user-owned fork under a different name.
